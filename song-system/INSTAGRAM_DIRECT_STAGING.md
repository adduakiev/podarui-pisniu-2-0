# Instagram Direct on staging

1. Use an isolated Node.js staging instance with HTTPS, a persistent disk, and one application instance. Set `LOCAL_ONLY=1` and point `DATA_DIR` at a dedicated writable staging directory. Set separate admin and session secrets. This repository's SQLite backend refuses Vercel and depends on a local persistent disk.
2. Use a Meta app with Instagram Login and a professional test Instagram account. Set the account ID and supported Graph API version from that app's configuration. Obtain an account token with `instagram_business_basic` and `instagram_business_manage_messages`. Confirm the app's access and reviewer requirements in its dashboard. [Meta Instagram API](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api)
3. Set `INSTAGRAM_DIRECT_APP_SECRET`, `INSTAGRAM_DIRECT_ACCESS_TOKEN` and `INSTAGRAM_DIRECT_VERIFY_TOKEN` in the staging server's secret settings. Generate a separate random verify token. Keep these values server-side.
4. Set `INSTAGRAM_DIRECT_ENABLED=1` on the staging instance when ready. Configure the callback at `/api/instagram/webhook` and subscribe the test account to message events. Run one inbound text test from an authorized test user, send a second message to check context, and request the producer. Verify that subsequent text reaches CRM while automatic replies are paused.
5. For rollback set `INSTAGRAM_DIRECT_ENABLED=0` and restart the staging instance. The route returns 404 when disabled and 503 if required configuration is missing. If a send fails, its reply remains in `instagram_inbound` with an empty `sentAt`. Review it before any manual retry because a timeout can occur after Meta accepted a send.

This slice handles inbound text on one configured Instagram account. Use the existing test suite to verify behavior with fake transport before enabling staging. Before connecting a customer-facing account, verify Meta's permissions and messaging policies, then address operational review of failed deliveries and traffic limits.
