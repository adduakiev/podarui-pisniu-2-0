# Telegram continuation requires web approval

An unbound `/start <code>` is a request to connect, not permission to read saved site context. The adapter creates a durable pending request and sends only: return to the existing web tab and confirm request number N. It does not load the conversation, run the interpreter, attach the Telegram identity to the order or disclose names/history/payment details. Pending inbound is retained in the delivery receipt, unassociated with the order's conversation; it is not automatically replayed after approval. The customer can send it again after connecting.

Back in the existing site chat, “Перевірити підключення Telegram” loads pending requests; focus also refreshes the view. Compare the displayed number with the number in **your** Telegram chat, tick the matching checkbox, then confirm that request. Reject unfamiliar requests. The number is a comparison label, not an authentication secret; no secret is typed into Telegram. A username is not used as proof of identity. The UI explicitly says that this confirms the channel, not a person.

`POST /api/telegram-binding` accepts the existing web chat `id/token` and action status/approve/reject/cancel. Every action checks same-origin and the existing HMAC chat token. Mutation also requires the exact pendingId belonging to that order. Status responses contain only pending IDs, comparison labels and expiry, plus bound/renewal state; no chat IDs or account names. Responses are no-store.

Pending validity is10 minutes, capped by the original link's24-hour expiration. Duplicate starts reuse the same pending request/label without extending its lifetime; previously sent updates retain existing transport dedupe behavior. Expired/rejected requests cannot be approved or silently reopened. The authorized web UI can explicitly cancel/replace the link after a closed request. Cancellation rotates the code and closes its pending requests; cancellation retries do not rotate again. Old codes and old pending IDs remain unusable for approval.

Approval is a synchronous SQLite transaction: it rechecks request state, expiry, current link, customer stop, existing binding for the order, and any other binding for the Telegram chat. Exactly one competing request can win. It cancels other pending requests for that order. An already-bound Telegram chat is never silently moved from another order by this web flow, even if it became bound after creating the pending request. Existing legacy duplicate link rows cannot add another chat to an already-bound order.

Approval itself does not introduce a new outbound sender. After successful binding, the customer returns to Telegram and sends a new message or a new `/start` update. The existing adapter then uses the saved context and existing producer/stop/revision/delivery guards. Replaying the original pre-approval update cannot reveal a newly private reply. Already-bound links retain their existing behavior. Native Telegram intake and an authenticated successor transition retain their internal bindings; low-level redemption no longer binds an unbound site bearer.
