# Site chat-first intake

The homepage and both song landing pages use one opening message/question form, with optional contact and format controls. No customer name or recipient input is required. `testMode` now controls only the synthetic-data notice and existing QA controls; it does not select a different intake flow. Landing recipient/occasion defaults and `source_page` still pass through the existing provisional-intent implementation.

For an opening-based POST, the site endpoint supplies explicit unknown labels (`name: Не вказано`, `contact: Чат сайту`, `recipient: Не вказано`) only when those properties are absent. These are compatibility placeholders, not inferred customer identity or verified contacts. Explicitly supplied fields still use the existing schema. Empty opening, invalid attribution, honeypot, same-origin and rate checks remain enforced. The browser intake guard and request-id/digest ownership logic are unchanged.

The order response issues its Telegram link through `telegramLink`, the same helper used by conversation responses. New links have a24-hour expiration immediately at issuance. Retrying an unexpired request reuses its existing order/link and does not extend expiration. Expired links are rejected at the exact boundary; renewal produces a new code. Existing chat binding prevents another Telegram chat from redeeming a bound link. No custom WebView authentication or new transport was added.

The chat offers the primary bot via the secure order link. “Залишитися тут” keeps the current web chat and hides the prominent Telegram suggestion for that order across reload using a browser-local preference. It does not grant authority or change order/channel state. An optional collapsed channel section remains available. WhatsApp contains a manually sendable order reference and explicitly states that the conversation history is not transferred automatically. Customer stop and producer controls retain their existing behavior; no auto-send is added.

Storage is a separate gate: actual local API tests require `LOCAL_ONLY=1`; `LOCAL_ONLY=0` still rejects local DB access. Rendering the form with `testMode=false` is tested under both flag values, but this does not claim that the application can run without configured persistence. Cloud persistence and production deployment remain out of scope.

Checks: `node --import tsx --test tests/site-chat-first.test.ts`, full available `tests/*.test.ts`, `npm run typecheck`, `npm run build`. For the mobile360 fixture, serve the production build with a fresh synthetic DATA_DIR, `LOCAL_ONLY=1`, `OLENA_RESPONSES_ENABLED=0`, `SESSION_SECRET=synthetic-only-session-secret-for-offline-qa`, and a local port. Set QA_BASE to that origin, QA_DATA to the same directory and QA_EVIDENCE to an empty output directory, then run `node tests/site-chat-mobile.cjs`. It uses real local APIs and only an injected fake Telegram transport. Do not use a live DB. All external browser requests are blocked.
